## What works (verified live, not just in CI)

- Full Iceberg read path: REST catalog (Lakekeeper) → S3 (SeaweedFS) →
  Avro manifests → Parquet → typed Datums, with projection + bounds/
  partition pruning, parallel scans, EXPLAIN pruning evidence.
- Time travel three ways: `snapshot_id` table option, query-level
  `FOR TIMESTAMP/VERSION/TAG AS OF` grammar (rule-storage stable),
  applied to foreign-table RTEs via the locking-clause position.
- v2 deletes: position deletes (exact per-file) + equality deletes
  (sequence-scoped, unpartitioned-only in M1 with loud errors).
- Conformance read-half: full primitive type matrix reads correctly
  from PyIceberg-written fixtures; Trino-written tables read correctly
  INCLUDING Trino's MoR position-delete file; snapshot agreement with
  Trino on every historical snapshot.
- TPC-DS SF=10 gate: q1–q10 all execute with 0 errors; pruning
  evidence 18,240 examined / 18,230 pruned / 10 tasks.

## Findings that cost time (and the lessons)

1. **Row-by-row row transport is THE bottleneck** (q3 full scale >60min
   CPU-bound vs 0.21s at 1% sample). Every future perf discussion starts
   here: slice 24 (columnar batch reads) is the single highest-leverage
   M2 item. Lesson: benchmark the transport, not the layout, when scans
   dominate.
2. **Rescan re-plan bug**: ReScanForeignScan re-planned (catalog
   round-trip + manifest fetch) per rescan; merge-join inner rescans
   fire it constantly. Fixed to rewind-only. Lesson: FDW ResScan is on
   the hot path of join execution plans — never do catalog I/O there.
3. **Correlated-subplan pathology**: q6 executes a full foreign scan of
   `item` per outer row (planner has no index to use). Recorded, fix
   path = remote parameterization or hash-subplan conversion (M2/M3).
   Lesson: FDW + correlated subqueries need a planned mitigation, not
   hope.
4. **LALR(1) grammar lesson**: per-table `FOR TIMESTAMP AS OF` after a
   from-item is unimplementable (collides with `FOR UPDATE` at 1-token
   lookahead; bison %expect 0). The locking-clause position gives the
   identical syntax query-level. Lesson: prototype grammar placement in
   bison BEFORE writing spec syntax commitments.
5. **meson test runs the INSTALLED binaries** (tmp_install): testing
   without `meson install` silently validates old code (cost one CI
   cycle + one stale-expected-file commit). `make lakehouse-check` now
   installs first.
6. **Lakekeeper serves per-table `s3.endpoint`** (container-scoped) that
   BEATS client config in pyiceberg — all host-side pyiceberg writes
   must run inside the compose network (docker run --network
   pgdatalake_default, venv mounted at its absolute path). Cost three
   debugging sessions before it was pinned down.
7. **PyIceberg quirks** (upstream, documented not worked around):
   `table.delete()` is COW (no delete files — our position-delete
   application needed a hand-built FFI test until Spark/Trino
   fixtures); `fixed[L]` written as ASCII hex strings instead of
   spec FLBA(L).
8. **Engine agreement is the best test oracle**: Trino reading the same
   snapshots matched our counts exactly, including Trino's own empty
   first append snapshot. Cross-engine fixtures (Trino in compose,
   proximaDB benchmark in flight) are now standing infrastructure.

## Scope notes for M2 planning

- Slice-20 delete application is read-side only; MoR fixtures for live
  verification arrive with our own M2 writer (or Spark).
- The M2 slice plan (HANDOFF) is written: writer → commit protocol →
  TableAM skeleton → INSERT → UPDATE/DELETE/TRUNCATE → MERGE + Trino
  reads a table we wrote.
- `lakehouse.optimize` design (doc 08 §2.1/§2.2) is M4; the bin-pack and
  partition-by manipulations used manually during this gate are its
  proof-of-concept.
