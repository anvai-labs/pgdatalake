# Self-hosted core and downstream service boundary

**Owner** Core packaging (06) publishes artifacts and conformance inputs. Qualification (08) owns independent examples and release receipts. Hosted or self-managed operators consume them. A contributor must be able to build, test, attach an Iceberg table and exercise qualified core behavior from a public checkout without a cloud service account. The initial supported artifact is a read-only FDW for one released PostgreSQL major. A fork build is a separate artifact with its own compatibility matrix. This is a proposed distribution contract.

## What belongs with the database

| Core-owned, available to self-hosters | Downstream operator-owned |
|---|---|
| FDW, TableAM, heap/WAL ledger and upgrade SQL, scoped object/catalog adapters including AWS/Azure/GCP data-plane authentication, reader, writer, safe recovery, receipts, core telemetry and operator-callable controls | Service provisioning identities, tenant placement, fleet routing and admission, quota and billing policy, account-specific IaC, deployment, on-call automation and service SLO receipts |
| Reproducible builds, SBOM and third-party notices, capability schemas, public fixtures, local reference deployment and instructions for backup, fencing and safely resuming publication | Deployment inventory, private account IDs and topology, cloud credentials and incident logs, hosted release promotion records and marketplace/commercial materials |

A safety fix, snapshot proof or migration required to read a customer's own data belongs in core. The service calls the same documented contracts as a self-hoster. Catalog credentials available to a query cannot provision VMs. Installation, upgrades and support tests in core never reference private code, private CI secrets or an operator's infra state. Retain PostgreSQL and third-party copyright and license notices in distributed artifacts. Review the extension's own licensing and dependency notices before first independent binary distribution. [PostgreSQL license](https://www.postgresql.org/about/licence/)

The first concrete exchange is the [stock smoke receipt](10-downstream-handoff.md#stock-reader-smoke-receipt-v1). A matching example makes a candidate eligible for a hosted test. Artifact provenance and production admission require additional evidence.

## Release manifest and consumer handshake

Proposed mandatory manifest fields are `contract_major/minor`, core commit SHA, source and artifact digest (including platform/architecture), signer/builder identity, PostgreSQL major/build flavor, extension version and allowed upgrade predecessors, ledger/receipt schema versions, capability set, and version plus digest of fixtures and qualification receipts. Capabilities name the operation, catalog/auth, storage API and format/delete profile; absence means disabled. Wire snapshot IDs use lossless decimal strings. Keep local C/Rust ABI handles process-local. Expose stable SQL operations and sanitized result states to external consumers. Monitoring fields may be additive and optional.

The producer publishes a candidate artifact by digest and a provenance attestation. A consumer verifies the expected repository/workflow, digest, schema range and capabilities, runs the same fixture bundle, and records its own config/infra revision and receipt. Pin the digest through canary, rollout and rollback. Never select a mutable branch/tag at service startup. For an incompatible change publish a new contract major with fixtures and an explicit migration or refusal. For additive changes introduce optional fields with defined defaults; old readers ignore unknown optional fields and reject unknown **required** semantics. A deployment may support two versions during transition only if both pass a matrix test. [Artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)

**Independent red test** Try the stock package on clean released PG with only read capabilities, and a consumer requesting `managed_append`. Expect stock SQL install and published reads to pass and that capability negotiation to fail before startup. Substitute a wrong digest, architecture, PG major or unknown required contract version; emit no traffic or catalog mutation. A consumer can keep serving its previous compatible digest while capability negotiation fails. Test install N, N→N+1 upgrade, logical dump/restore and a mixed-version refusal. Binary rollback after a ledger upgrade is permitted only if the old build can read every live attempt and receipt. Otherwise quiesce, roll forward or restore/reconcile under fencing. Preserve unresolved attempts and payloads across upgrades. Include actual stock and fork receipts before labelling either deliverable supported.
