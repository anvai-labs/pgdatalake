# Managed write handles and snapshot inclusion

**Owners** Module 03 owns capture, the source write identity, exact membership and MVCC visibility. Module 04 owns the durable publication result. Module 01 proves catalog inclusion. Module 06 exposes authorization, SQL types and deadline handling. Module 08 supplies the independent oracle. These are proposed SQL semantics. Extension 1.6 provides private ledger primitives. It has no qualified customer wait API.

## Interface for a driver or pool

1. In the writing transaction request an opaque write handle for the table and the caller's staged work. Persist its ID, source cluster incarnation, tenant/database, binding generation, authority, table UUID/ref, immutable segment IDs or durable membership reference and payload digest with the source transaction. If multiple segments are emitted at pre-commit, bind them atomically before the handle becomes visible to other sessions. Savepoint rollback excludes the corresponding members. A handle proves nothing until its source transaction commits. Return a handle per table or an explicit list for a transaction touching several tables.
2. `wait_publication(handle, timeout)` runs in a **fresh statement after COMMIT** on an authorized primary connection. Resolve the durable handle to every constituent batch. A write can span multiple batches and a batch can contain several writes. A successful answer requires verified coverage of **all** handle members at a single retained pin on the intended ref. If early deployment limits a write to one batch, reject oversize writes before acknowledging their source commit. Inside the uncommitted source transaction reject the wait immediately. Polling uses an interruptible monotonic deadline; cancellation stops the waiter only.
3. Return `{write_id, state, binding, introducing_snapshots[], selected_snapshot?, reason, retry_handle}` subject to current SQL privileges. `pending` means known committed source work awaiting evidence. `unresolved` means a send or its proof has unknown disposition. A bounded timeout returns the last durable state with `deadline_elapsed`. `verified` names a proven pin. Unknown/rolled-back/unauthorized handles disclose no other tenant's state. Receipts contain no bearer credential, raw endpoint secret or payload. The service routes SQL; an ordinary connection pool can reconnect to `rw` and pass the same handle.
4. For a fresh published read use `verify_inclusion(binding, write, selected_pin)`. Compare tenant/authority/table UUID/ref and the trusted introducing evidence, then walk retained ancestry on that ref or use equally strong retained proof. Numeric snapshot ordering, row equality, a manifest timestamp and WAL LSN do not prove inclusion. Pin the actual execution to the checked snapshot. For an external engine return the UUID and exact snapshot ID and require it to use that pin with its own authorized credentials. Historical acceptance and current-lineage inclusion are separate results.

The shared selection fixture assumes an already authenticated binding, a verified introduction, and loaded metadata for the selected pin. Live tests must establish each precondition. An append introduced at `9007199254740993` may be an ancestor of snapshot `17`. Return included there if the parent chain verifies. If `main` moves to the pre-append parent, report `outside_lineage` for that selection. A replacement UUID yields `binding_changed`. Missing parent history yields `insufficient_history`. Never reinterpret any of these as permission to replay. A later legitimate overwrite/delete may change the row at an inclusive descendant. Preserve 64-bit IDs exactly across SQL, JSON and client boundaries (decimal strings in JSON). A restored cluster can read old receipts only after lineage and the local recovery horizon are verified. ## Managed scan and recovery gates

| Situation | Observation before returning the first row |
|---|---|
| Committed INSERT, retained base 100 containing `[10]`, segment 7 containing `[20]` | Own prior command sees 20. Another session before COMMIT sees `[10]`. A fresh authorized primary read afterwards returns `[10,20]`. Until verified publication a published read at 100 still returns `[10]`. Roll back 7 instead and both return `[10]`. |
| 7 and 8 each contain 20, one batch at 101 | PG snapshot between source commits gets base 100 plus 7 = `[10,20]`. After both commits use 101 = `[10,20,20]`. If the older base/proof has expired, fail the older statement before output. COUNT and rescans use the identical cut. Complete membership must include locally invisible members. |
| A catalog POST for 7 succeeds but reply is lost; 8 arrives later | Keep the original bytes and intent, hold 7 lookup-only. Verify its snapshot, finalize only 7. 8 remains pending. An authorized managed read suppresses 7 exactly once on the inclusive pin and includes 8 only if PG-visible. Preserve older payloads while supported snapshots need them. |
| Repeated table aliases or a join | Reuse the same pin per binding within the statement and one PG snapshot for local visibility. For two different tables resolve the whole vector before producing output. Independent table pins can straddle an external transaction. Require an explicit joint-cut provider to promise atomic multi-table external publication. Gate long-lived managed Repeatable Read, Serializable, staged UPDATE/DELETE and standby reads separately. |

Retain source authority, table UUID, approved root, ref and configuration generation when enrolling the table. Verify binding once at enrollment and invalidate on rebind. Capture under SQL/DDL locking in the source transaction, preserving prior qualified identity even after rename/drop/OID reuse. Never adopt ambiguous unbound legacy rows. Restart recovery uses the recorded original route and scoped credentials. A changed or unprovable authority holds work unresolved. A source commit and its pre-POST intent must survive every failure advertised by its durability profile. The live 1.6 `authorize_publication_send` sets `synchronous_commit=local`. A synchronous HA profile requires a new durability barrier for **both** source commits and send intents on the actual promotion candidate. Test WAL flush/replay on its system ID and timeline. On missing proof fence new sends and hold recovery. A later standby-routing feature must separately prove actual commit replay and compatible Iceberg membership. [PostgreSQL WAL durability](https://www.postgresql.org/docs/current/runtime-config-wal.html) · [Publisher takeover](04a-publisher-recovery.md)

**Independent test** Use a stateful fake catalog and two SQL connections to replay the membership and receipt vectors with expected pins, row multiplicities and zero extra submits after timeout, reconnection or a rolled-back ref. Run the same assertions against ordinary INSERT → worker → fresh FDW/Trino, with a kill after catalog acceptance. Provider tests and the example oracle permit integration; this last run is the managed release gate.
