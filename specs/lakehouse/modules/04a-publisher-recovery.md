# Staged append recovery

**Implementation slice for M2, proposed 2026-11-21.** Lakekeeper accepts a staged append, the reply is lost, and a second segment arrives. After restart, an external reader must see the original row once, the receipt must identify its snapshot, and the second segment must remain eligible. The first profile covers appends from one PostgreSQL ledger to a bound Iceberg table on `main`.

## Durable transitions and ownership

| Boundary | Required durable action | What a replacement worker may do |
|---|---|---|
| 1. Claim, in a short PG transaction | Persist the exact bounded set of committed segments, operation ID and immutable input digest. Enforce exclusive segment membership and one unresolved claim per ledger and remote target (authority, UUID and ref), including aliases. | Acquire the existing claim with a new generation. Later inserts stay eligible for a separate claim. Other tables can progress independently. |
| 2. Prepare, outside the PG transaction | Using the bound UUID, ref, schema and spec, build immutable objects. Pin the attempt to an expected parent (or empty ref). Include the operation ID and input digest in the proposed snapshot summary. Preparation can upload objects but cannot move the catalog ref. | Resume or rebuild an unsent proposal from the same logical inputs. Preserve objects referenced by any unresolved attempt through cleanup. |
| 3. Authorize one send, in a short PG transaction | Compare owner generation and state. Record attempt number, expected parent, proposed snapshot ID, immutable proposal identity and a **may have been sent** state. Flush the commit WAL locally before dispatch, including when foreground writers use asynchronous commit. Only the worker that committed this transition gets to send. | A stale generation fails the transition. After the durable commit, every recovery starts with lookup, including a crash before the socket write. |
| 4. Send, outside the PG transaction | Submit that proposal once with UUID and exact expected-ref preconditions. Return a typed result carrying evidence for this attempt. A timeout, disconnect or undecodable success response after dispatch leaves the outcome unknown. | Apply the evidence rules below. Lease expiry fences local ledger changes. The earlier remote request can still arrive. |
| 5. Finalize, in a short PG transaction | Verify generation, binding, operation, digest and accepted snapshot. Join the stored claim members to the ledger. Update the exact set, compare cardinality, and persist the receipt in the same commit. A mismatch aborts this transaction and requires investigation. | An already finalized matching receipt is an idempotent success. A failed local commit leaves the same attempt recoverable by lookup. Reader retention governs when its segment data and membership evidence can be retired. |

The ledger owner supplies the atomic transitions, uniqueness constraints and upgrade. The publisher owns the decisions. The writer supplies a prepared immutable proposal. The catalog adapter submits one attempt and looks up its evidence. The current Rust commit helper can replan on a conflict inside one C call. Use a single-attempt path for staged publication so each new proposal has a durable record before dispatch. Keep catalog tokens and signed URLs out of records and receipts. ## Local claim provider in extension 1.4

The first implemented boundary is the short PostgreSQL claim transaction. The private provider accepts a caller-generated operation UUID, catalog authority UUID, Iceberg table UUID, source relation OID and 1–1024 distinct segment IDs. The supported ref is `main`. The authority identifies the canonical catalog scope across local server aliases. A catalog/writer integration must establish that scope and verify the remote UUID before producing a bound segment. TableAM capture still produces legacy rows by default.

A bound append supplies its identity at insertion. The database hashes its payload once and prevents changes to its identity, bytes, row count and segment ID. The claim takes row locks in segment order, compares exact cardinality and stores the operation and exclusive members in one transaction. A unique index reserves the remote target across local aliases while a claim is unresolved. Source transaction visibility remains on the individual segment rows. The digest is SHA-256 over the concatenation, in ascending segment ID order, of the 8-byte ID and 4-byte row count (both signed, network byte order) and 32-byte payload SHA-256. Claiming reads at most 44 KiB of digest inputs. Capturing, sorting IDs and PostgreSQL row/index work have separate costs.

A caller that loses its local acknowledgment retries with the same operation and member set. A committed match returns the stored digest. Reusing the ID for a different binding or members raises `22023`. A conflicting reservation raises `40001`. Missing, unbound, published or wrong-source inputs fail the whole acquisition. The adapter has invoker rights and no PUBLIC execution privilege. Local acquisition supplies no authority to send a request.

**Cutover.** Deploy the new library and restart publisher workers and backends that loaded the old one before enabling a bound capture producer. Upgrade using `ALTER EXTENSION lakehouse UPDATE`. The nullable binding columns preserve existing rows without a payload backfill. A legacy row keeps its original publisher for its lifetime. An operator investigating ambiguous history must reconcile it before resuming a legacy publisher. The legacy worker discovers and emits only unbound rows. Its row locks reject stale repeatable-read selection before dispatch. Verified capture and compatible-pin reads remain delivery gates. The catalog adapter still needs to consume the local send and receipt transitions. A physical PostgreSQL crash restart tests local WAL recovery. Database restore and failover require a ledger with all send intents and single-writer fencing.

The [claim smoke](../../../src/test/lakehouse/fixtures/publication-claim-check.py) races identical and aliased inputs, exercises the 1024-member bound and independently computes the digest. Trino checks the difference from the pre-publication snapshot set and reads the resulting row. The CI fixture performs an immediate PostgreSQL restart after a committed claim and checks its digest and membership again.

## Send intent and receipts in extension 1.5

The private ledger exposes three transitions. The scheduler uses a compare-and-advance token to acquire or transfer a claim. This transfers the right to make local state changes. It cannot revoke a send already authorized in an earlier generation.

| Transition | Requirement |
|---|---|
| `advance_publication_generation` | Compare the caller's generation to the unresolved claim's current token. A newly created claim starts at zero. The first owner advances it to one. A failed comparison raises `40001`. The scheduler owns lease policy. |
| `authorize_publication_send` | Execute as a standalone top-level `CALL` on a worker connection outside an explicit transaction. It checks the current generation and input digest, stores the expected parent (NULL for an empty ref), proposed snapshot ID, and SHA-256 digest of the exact prepared request bytes. It commits with local synchronous WAL flush before returning the transaction ID. Dispatch requires a successful response to this call. Any existing attempt is lookup-only, including when the local reply is lost or a new generation takes ownership. |
| `finalize_publication` | Submit the acceptance evidence the catalog adapter verified. The current generation, authority, table UUID, input digest, snapshot and proposal digest must match. Update exactly the stored members and the receipt in one transaction. A member mismatch rolls the update back. Repeating the same finalization in the same generation returns the existing cardinality. Use a locally synchronous commit and acknowledge the receipt after that commit. |

The 1.5 provider retains one immutable attempt per claim. It supports a lookup-only hold and finalization on proven acceptance. A later transition must add durable evidence of definitive rejection before a second attempt becomes eligible. The full publisher still needs verified capture and binding, immutable request preparation, the single-attempt catalog adapter, and worker integration. Keep the prepared request and its expected snapshot fields available to recovery. Catalog lookup verifies provenance and compares the introducing snapshot and immutable manifests against that proposal before asserting its digest. The digest of a serialized POST body cannot be reconstructed from a snapshot summary alone. The `fsync` prerequisite covers the local primary. Failover and restored copies require the ledger and single-writer guarantees in the recovery contract.

The [intent smoke](../../../src/test/lakehouse/fixtures/publication-intent-check.py) upgrades a 1.4 claim, parks and fences an old owner, races two current authorizers, and inspects the winner's WAL commit record with `pg_walinspect`. It repeats authorization after an immediate database restart and exercises rollback, mismatched evidence, exact segment completion, and a second claim.

## Exact proposal retention in extension 1.6

The authorization call now takes the exact prepared POST body as `bytea` in addition to its SHA-256 digest. The worker supplies the body, digest, expected parent and proposed snapshot ID from the same prepared Rust value. PostgreSQL validates the 1–65,536 byte bound and independently hashes the received bytes. It commits those bytes, the generation and the attempt identity in the same locally flushed transaction before allowing the send. This byte limit covers the request envelope. Payloads, Parquet files and manifest contents live in their existing objects. The staged Rust provider rejects oversized requests and credential-bearing or signed storage locations before authorization.

A recovery worker reads the exact body with its retained hash and binding. It passes that proposal to the read-only catalog lookup. The provider checks the introducing snapshot and reads its manifest list through the bounded storage adapter. The worker supplies the independently verified authority, table root and budget. The authorization API forbids another send even if the original worker has disappeared. The ledger rejects attempt edits, deletes and truncation until a receipt-aware retention path is added.

The upgrade preserves digest-only 1.5 intents with a NULL body. They stay reserved for lookup and require independently retained bytes matching the original digest for verification. A missing proposal and insufficient catalog evidence require a hold. The migration cannot infer what was sent from the catalog's current state.

The [intent smoke](../../../src/test/lakehouse/fixtures/publication-intent-check.py) verifies upgrade from 1.5, SHA-256 mismatch, bounds, immutable storage, exact recovery after immediate restart and an unchanged send fence for older intents.

The [catalog lookup provider](01-catalog-storage.md#acceptance-lookup-for-a-retained-proposal) holds an attempt when it cannot prove positive acceptance. The HTTP test first sees the old head, delivers the original POST, loses the reply and checks that the next lookup verifies the introducing snapshot under a later head. No definitive rejection transition is implied by a missing marker.

## Prepare immutable writer output

The writer stages append-only files with create-only PUTs and passes their data descriptors and the verified writer pin to `CatalogClient::prepare_staged_append`. This Rust entry point reloads the bound catalog route and checks the UUID, `main` head, sequence, schema, spec, base manifest-list URI and table root against the writer pin. A moved pin fails before new metadata uploads. Unique nonempty file descriptors must be under the bound data directory.

The parent manifest list is read with the object byte budget and deadline used by recovery. Preparation carries the parent's data and delete manifest references forward within the bound metadata root. The new list must fit the same budget before its new manifests are uploaded. New Parquet files, manifests and lists use conditional create at their generated keys. A collision leaves the existing object intact. The writer seals the new list and returns the exact CAS request, which the worker can authorize and submit separately.

A failed preparation can leave unreferenced files, including if the store returns an uncertain PUT result. Proposed objects must survive recovery and cleanup while a send is unresolved. Automatic orphan reclamation remains a separate gate. This provider consumes a verified binding and an in-band Iceberg v2 pin. Binding enrollment, foreground capture and publisher orchestration remain dependencies.

## When a second append is safe

| Evidence | Decision |
|---|---|
| The provider proves that the recorded proposal was accepted on the intended UUID/ref, with the matching operation ID, digest and proposed snapshot. | Complete using the introducing snapshot ID, even if a later compatible append advanced the head. The visibility module separately proves membership for each requested read pin. |
| The provider proves that the **one authorized send** for this attempt definitively failed its expected-base check and can have no later effect. | Record the rejection under the current generation. Reload the binding and validate schema, partition spec and write profile. If compatible, prepare a new attempt with the same operation, digest and member set. If incompatible, hold the claim and surface the conflict. |
| Lookup sees an unchanged head, a missing marker, expired evidence, a replaced UUID or contradictory markers. A paused submitter or a request in transit could still take effect. | Preserve the claim and receipt. Retry **lookup only** with bounded backoff. Expose the reason and pending age. Impose the same proof requirement on manual recovery. The receipt can remain unresolved indefinitely if the provider loses the evidence. |

For the first profile, disable transparent resubmission of commit requests throughout the client stack. A marker proves inclusion only when the provider can verify its origin and match the recorded proposal. A crash between authorizing and sending can leave a claim waiting indefinitely on a catalog that only recognizes successful commits. The configured flush time is an eligibility target. Recovery after database restore or failover requires a ledger retaining every send intent and a single active writer, or separate reconciliation before resuming publication.

The `publish_recovery_cases` fixture inherits the binding, operation ID, base and claim from `publish_reply_lost`. Each case starts afresh with the first proposal prepared against 100. Count actual commit requests at the catalog boundary, including rejected requests. Count accepted snapshots for this operation only. At a checkpoint, drive recovery up to the next scripted external event and inspect the ledger and transport. For `lookup_only`, advance the fake clock through another retry and prove the claim is still reserved and only lookups occur. For `prepare_same_claim`, the next submission must carry the original ID and digest.
