# Core and operator integration handoff

The first independently usable boundary is a stock reader on PostgreSQL 19. Core qualification can prove exact SQL results on the reference catalog. An operator can develop candidate selection with a local example, then run it on evidence from the same core build it plans to test. The operator owns the decision to send traffic. This module defines the inputs that can cross that boundary and the work that can proceed before real infrastructure is available.

## Stock reader smoke receipt v1

Run the stock smoke with `--receipt PATH` on a clean candidate checkout and a disposable stock installation. It writes JSON after the live checks and cleanup succeed. Fork CI retains `stock-reader-receipt` and a separate `stock-reader-test-package` for seven days. The package contains the installed module, control file and SQL install script. For a joined test choose the successful public run by source SHA, download both artifacts from that run, and hash the module independently. These test artifacts have no production release attestation. The checkout SHA on a PR can describe a synthetic merge. Use the post-merge run when pinning the branch revision. An absent receipt supplies no positive evidence. The synthetic example and consumer cases have no deployment authority. | Fields | Wire rule |
|---|---|
| `contract_major`, `contract_minor` | JSON integers. Major 1 fixes the meanings below. Accept additive minor versions with unknown optional fields. A new mandatory interpretation needs a new major. |
| `core_sha`, `module_sha256`, `platform` | Lowercase 40-hex Git revision, lowercase 64-hex SHA-256 of the tested shared library on the server, and lowercase OS-machine. The initial consumer qualifies only `linux-x86_64`. The service compares with independent candidate inputs. A checksum copied out of the same untrusted receipt cannot authenticate the file. |
| `profile`, `server_version_num`, `extension_version` | Exact reference profile from the fixture, integer PG19 server version and stock extension version. A SeaweedFS result covers the S3-compatible fixture. Different versions, real object stores, credentials and cloud placements require their own capability evidence. |
| `passed` | Unique names of checks completed in this run. Select only required checks that the consumer understands and that the producer passed. Unrecognized offered checks grant no capability. |
| `parent`, `child` | Each contains a canonical signed 64-bit decimal string `snapshot_id` and ordered integer `rows` for this synthetic table. IDs must differ. The child can have a smaller numeric ID. Preserve duplicate 20s in the parent. The producer compared both live and restored PostgreSQL with Trino at each selected pin. |

The consumer request contains `core_sha`, `module_sha256`, `platform`, `profile` and a nonempty unique `required` list. Both sides use the literal case IDs and expected decisions in the fixture. Apply the decision rules in order: decode the major; reject unsupported majors; check required field types; match the profile; match build identity, PG major and extension; check capabilities; check pins and exact rows. Success is `eligible_for_hosted_test`. Failure returns the first reason. Neither result starts a deployment or validates signatures. The operator must verify the receipt's source/run, obtain trusted artifact expectations and qualify tenant isolation, its cloud profile, and a real authenticated SQL route separately.

## Change and merge order

1. Identify the producer, consumer, retained state, expected failure and observable example for a single seam. Add the failing example to core. The consumer can use the proposed fixture bytes by digest in a local checkout immediately.
2. Core lands a backward-compatible contract and producer smoke on its own public CI. Publish the exact SHA, digest of each changed input, fixture case IDs and supported/unsupported behavior. Add private policy and privileges only downstream.
3. The operator updates its lock in one reviewed change, replays those same cases through its own code, then tests an actual producer receipt and records both SHAs. On incompatibility keep the previous lock and candidate. For a new major, support both while migrating or refuse the incompatible combination before routing.
4. A joined gate needs both providers' observations on the same profile. Archive the candidate digest, role/binding generation, pins, row multiplicity, request counts and result reason. Track producer pass, consumer replay and hosted qualification separately. Freeze release/ABI/ledger meaning at the producer; version behaviors that change evidence or retry decisions.

**Stop detailing a seam** once each owner can independently write a failing test and both agree on the first visible result and failure owner. Open the next contract only when the next milestone needs it. The published reader can proceed while the managed recovery and sleep protocols are still behind their own gates.

For per-viewer published reads, implement the proposed [06c provider and
consumer boundary](06c-governed-published-read.md) against its versioned
fixture. Existing stock/scoped-reader receipts qualify only their recorded
profiles. A protected route also requires delegated identity, a governed
source pin, exact visible rows and independent request observations.
