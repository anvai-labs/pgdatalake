# Cloud catalog and object storage profiles

**Owner** Module 01 maintains catalog and object adapters. Module 08 verifies per-operation support; deployment teams qualify compute independently. A profile ID names a versioned combination of cloud, region, endpoint/authority, catalog implementation/version, auth flow, object API, format/delete features, and operation. Qualify reads, conditional object creation, catalog commits, recovery lookup, reader capacity and writer failover independently. A tenant can bring a different catalog hosted on the same cloud. Default each untested cell to **NOT RUN**.

## Data plane the core must provide

Module 06 selects an authorized mapping. Module 01 provides `resolve(binding, selector, principal, deadline) → Pin | denied | changed_binding | pin_unavailable | unsupported | unavailable`. It also provides `read_range(scope, object_version, offset, length, deadline)` and `create_immutable(scope, key, bytes, deadline) → created | exists | unknown`. A create timeout reserves the original name until evidence resolves it. For publication evidence read fresh, bounded bytes and compare SHA-256 independently. Use the cloud ETag/generation as an object validator where appropriate. Catalog CAS remains the only operation advancing the table ref. Enforce both configured root and freshly resolved table root for all manifest, data and delete reads. Parse bucket/account/container and key component boundaries before checking scope. An object path prefix alone is an inadequate identity.

Keep the catalog token, object credential, PG role and provisioning identity distinct. A profile stores credential **references**, audience, permitted operation and binding generation. Re-resolve on rotation. Cache keys include authority, tenant/security scope, version and range. Recheck authorization before serving shared cached bytes. Expiry during a read permits a bounded refresh for the same principal and pin. Authority change, revocation or a new root requires reauthorization. No credentials in receipts, traces, query plans, fixtures or persistent request bytes. Never replay a catalog mutation as a side effect of refresh.

### Hive migration contract

1. For a Hive Metastore entry that already points to Iceberg metadata, choose one catalog authority and measure exact-pin read equivalence at the old and target surfaces. Pin the metadata location, UUID, selected snapshot and roots. An operator may keep the source read-only during a rehearsed cutover. Pause source writes and maintenance that could delete referenced files until target validation and rollback decisions finish.
2. For ordinary Hive tables, use the upstream Iceberg conversion workflow that matches the migration. Prefer the Spark Iceberg `snapshot` procedure for a reversible comparison. It shares underlying files, so verify the source retention policy before relying on it. Treat `migrate` and `add_files` as operator-approved changes. Validate schema, partitions, exact rows and supported formats. The first PostgreSQL migration profile reads Parquet inside the qualified Iceberg format and delete scope. [Iceberg migration procedures](https://iceberg.apache.org/docs/latest/hive-migration/)
3. Prevent competing commits to the same table through different authorities. Qualify cutover and rollback by recording the original and target pin, retained file ownership and query digests. Keep writes disabled on the migration profile. A migration failure leaves the original authority available for replay.

### Implementation seam for parallel work

Core catalog/storage (01) maps one independently enrolled authority, route, authentication mode, table UUID, ref and root to a pinned read plan or a typed refusal. SQL/packaging (06) resolves PostgreSQL permissions and the mapping, and passes that authority without a per-catalog SQL fork. The reader (02) consumes an authorized pin and scoped object access. Use the [existing v1 observation and refusal contract](06b-scoped-read-handoff.md) for fixture-driven consumer work. If a profile needs fields that change authority or retry semantics, review the provider and consumer fixtures together before enabling the path.

Exact snapshot selection uses the currently authorized metadata's standard Iceberg
`snapshots` array. One metadata observation suffices to select a retained pin or
return pin unavailable. The provider's advertised window governs both outcomes.
The initial xCatalog profile uses unchanged-schema, URI-backed Iceberg v2 tables
with explicit generation files. Each provider qualifies its schema, delete and
retention policies.

Start each new adapter against the same pinned parent and child row multisets with a wrong-UUID target, adjacent denied root, expired credential and missing pin. Test response-provided routes and credentials against the enrolled policy before making any object request. Count approved requests and bytes, assert zero forbidden object requests and reject unsupported governance directives. Obtain an independent-engine match before profiling. For later write cells, repeat the same lost-reply one-POST recovery and immutable-create gates. No profile can inherit a write or read claim solely from implementing the REST protocol.

## Independent acceptance

For each catalog and storage pair exercise two separately authorized tenants, sibling roots, rotating credentials and a reference reader. Collect exact pins, row multiplicity, SDK requests and byte counts. Require one bounded fresh object read, a denied out-of-scope object before access, and exact pinned row multiplicities. For a write profile additionally verify an immutable create collision preserving the original bytes and record one catalog acceptance after a lost reply and verify the original operation. Test single-request and multipart/resumable variants separately. Emulator success enables integration. A live profile records region, artifact, catalog and engine versions, permissions, operation, result and receipt. Read-only qualification can ship independently of publication.
