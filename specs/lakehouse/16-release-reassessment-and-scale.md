# Lakehouse milestone reassessment and execution at scale

**Decision for `perf-release` at `eb8e3602179` (2026-11-21). Hold release qualification.** Ranged and projected reads, lazy projected batches and the typed batch ABI are sound directions. The new COUNT paths and staged publisher need correctness work before their timings or guarantees can qualify a release. M3 remains in progress. This document updates the status of [the original review](13-implementation-review.md) and sets acceptance criteria for the next performance milestone.

## Evidence

- Local `cargo test --locked --offline -p pgdatalake-core` passed 118 tests with one manual benchmark ignored. Tests cover consecutive append history assembly, conflict handling, projection and byte reuse, and v3 deletion-vector fixtures.
- A fresh GCC 14 assertion-enabled native build passed all 243 upstream regression subtests and all 11 lakehouse SQL groups. A supplemental test with a disposable database reproduced two failures. A generic prepared managed COUNT returned 2 before and after a committed third row. A fresh COUNT returned 3 and the scan returned IDs 1, 2 and 3. A separate transaction inserting one row into each of 65 managed staged relations committed successfully but produced only 64 ledger entries for those relations.
- The original time-travel deparse failure reproduced on this build. `pg_get_viewdef` omitted the version selector from a view created with `FOR VERSION AS OF 17`. A logical dump and restore still needs its own acceptance test.
- GitHub's fork workload passed for [managed COUNT PR #27](https://github.com/anvai-labs/pgdatalake/actions/runs/44932023945/job/136930580733) and both [native](https://github.com/anvai-labs/pgdatalake/actions/runs/44933630172/job/136935555646) and [Rust](https://github.com/anvai-labs/pgdatalake/actions/runs/44933630172/job/136935555700) jobs for lazy decode PR #28. The managed COUNT regression checks an offline staged table, a savepoint rollback and a filtered negative control.
- The latest handoff records fast metadata-only COUNT on SF10 and an SF10 q1 timeout above 600 seconds. A metadata COUNT receipt measures a different path from a scan, filter or grouped aggregate. Full q2/q3 results, result digests and concurrency/RSS curves are absent from the handoff. [Measurements and limitations](HANDOFF-TAKEOVER.md)

This review did not rerun full SF10, four-store interop, the publication fault matrix, or a dump/restore. Treat the corresponding gates as NOT RUN on this candidate.

## Correctness gates for the current milestone

### COUNT must be computed at execution

The managed hook replaces the query with a constant and removes the relation range table and FROM list. This drops the plan's ordinary relation permission checks, RTE security quals and relation dependencies. Eligibility does not establish built-in COUNT identity, RLS absence, no inherited children, or a complete staged-only source. An empty published ledger does not prove the remote table is empty. The prepared-plan test above reproduces the stale result. The legacy-NULL guard reads a bigint counter with `DatumGetBool`. Use a SQL boolean or decode the count as bigint before comparison. The current ledger declares `row_count integer`, so its sum is bigint. Preserve that result type explicitly through any ledger upgrade. [Managed hook and ledger query](../../src/backend/access/lakehouse/count_elision.c) · [Ledger schema](../../src/backend/access/lakehouse/lakehouse--1.2.sql) · [Regression](../../src/test/regress/lakehouse/sql/count_elision.sql)

The FDW upper path carries a plan-time count and reopens the scan in Begin. It compares totals without rechecking delete eligibility. A snapshot can add deletes without changing the physical record count. A prepared plan can also retry the same constant after a mismatch. Iterate reads the relation descriptor before its elision branch even though the upper scan has no base relation. Fix that initialization as part of replacing the constant. [FDW upper path](../../src/backend/access/lakehouse/fdw_plan.c) · [FDW iterator](../../src/backend/access/lakehouse/fdw_exec.c)

**Required.** Gate the current implementations off until an execution-time metadata path preserves PostgreSQL permissions, RLS, snapshot semantics and base dependencies. Use a one-row upper path for the FDW and an executor path retaining the relation and permission metadata for managed scans. Pass a plan descriptor with operator identity, projection, selector and fallback, without embedding a count. Resolve the supported snapshot at execution and prove delete eligibility before returning the checked bigint count. If proof fails, execute the ordinary aggregate. For managed tables, enable an offline optimization only with an explicit proof that the local ledger covers the entire table and the current statement's visible rows. Decode SPI values by declared type and check overflow. Keep `LIMIT 0` and normal permissions intact. Defer published and staged combined counts until the publisher visibility contract is implemented. **Gate landed 2026-11-21:** the managed planner hook (former `count_elision.c`) is deleted and the FDW upper Const path is unwired, both with the contract regression (`count_elision.sql`) in the same commit. The legacy-NULL `DatumGetBool`-on-bigint guard died with the gated file and must not return; decode the count as bigint before any comparison in the successor.

**Acceptance.** Compare optimized and ordinary counts through PREPARE/EXECUTE across commits, same-count snapshot changes with deletes, existing remote rows with no ledger, own writes and canceled attempts. Cover legitimate and denied reads, invoker/definer views, RLS, inherited tables, `LIMIT 0`, legacy NULL counts and a same-named aggregate. For each optimization, validate EXPLAIN shape and catalog/data request counts. [Original aggregate spec](15-staged-writes-and-caching.md#66-metadata-elision-for-trivial-aggregates-planned--p0b4)

### Publishing must reconcile remote success with local visibility

The publisher selects all unpublished segments without claiming an exact set, commits to Iceberg, then updates all unpublished rows for a relation. A concurrent INSERT can create a segment between selection and update. A manual publisher and worker can also select the same segments. A crash after remote success can cause repeat publication. A reader currently filters by local `published`, independent of the pinned Iceberg snapshot. Old remote plus new ledger can omit the delta. New remote plus old ledger can duplicate it. The staged pre-commit pass captures at most 64 table entries and silently skips further entries. **Capture fix landed 2026-11-21:** the pre-commit collector now sizes its list from the hash itself (no fixed cap), and the bulk regression (65 staged relations in one transaction, 65 ledger segments, read-your-writes on the last relation) is in `staged_insert.sql`. The rest of this section — durable claims with exact segment IDs, ambiguous-remote-commit reconciliation, visibility watermarks — remains open. [Publication and ledger update](../../src/backend/access/lakehouse/publisher.c) · [Staging and read overlay](../../src/backend/access/lakehouse/tableam.c)

**Required.** Use a bounded, durable batch claim with explicit segment IDs and a stable operation ID. Serialize publication for a table and verify exact update cardinality. Reconcile an unknown result by confirming the operation on the target UUID before retry. Resolve ledger visibility against the pinned remote snapshot's ancestry or a verified publication watermark. Define conservative behavior if a published snapshot is expired before reconciliation. Apply the same rule to reads and aggregate paths. Reject or process excess staged tables before PRE_COMMIT can silently discard any rows. Enforce owner or explicit delegation on manual publish and publisher control.

**Acceptance.** Use fault barriers before upload, after catalog success, before local ledger commit, and across a second publisher or concurrent INSERT. Verify exact row IDs in SQL after restart and with an independent remote reader after publication settles. Include 65 staged relations and concurrent reads pinning before and after the remote commit. Track pending bytes, oldest segment age, commit conflicts, retries and reconciliation backlog.

### Lazy reads need an end-to-end resource contract

P0b3 removes eager collection from the projected reader. The all-columns reader still fetches and decodes the entire file. PR #28 changes one Rust source file and adds no dedicated early-stop counter test. The prior ranged test checks projected bytes and cache hits and the row-equivalence test drains the reader. These checks establish different properties from bounded live memory, first-row cost and late-corruption handling. [Parquet readers and tests](../../src/backend/access/lakehouse/core/pgdatalake-core/src/parquet.rs)

**Required.** Use one fallible, incremental reader for projected, full-column and delete work with explicit cancellation and bounded buffers. Resolve FDW projection from target, local quals and delete keys. Represent zero output columns separately from “all columns”. Avoid one network request for each tiny sequential parser read. Account for fetch, decode, transport, and the backing allocations retained by slices.

**Acceptance.** In a cold multi-row-group fixture, `LIMIT 1` must read no later-group data pages. Force a later-group decode error and verify the full scan errors while the short scan completes. Scale row-group count at fixed width and record peak live decode allocation and RSS. Verify absolute positions under deletes, unsupported types and reordered fields. Cancel a blocked fetch through PostgreSQL and verify the next command succeeds without leaked scan state.

## Execution design for the next milestone

1. **One execution description per statement and remote identity.** Separate estimates from executable tasks. Make default EXPLAIN avoid data and delete objects. Enable explicit opt-in for remote estimates. At execution pin the table UUID, snapshot, schema/spec IDs, required field IDs and task/delete applicability. Key statement-local reuse on the permission scope, snapshot, required fields and predicates. Pass workers the same work description and claim indices from it. Reuse the pinned description on rescans. An estimate failure may fall back to local estimates. Invalid executable metadata needs a useful error.
2. **Bound request amplification and memory before increasing parallelism.** Reuse authorized clients per execution. Use manifest lengths where valid, coalesce nearby reads into aligned blocks, and fetch only the needed column chunks and indexes. Run bounded prefetch under byte and request quotas with cancellation and backpressure. Account for compressed cached data, decoded batches, delete indexes, outstanding I/O and aggregate memory. Set query-wide and per-process budgets and cap the sum across workers. Bound each publisher claim by bytes, rows, segment count and elapsed time. Apply backpressure on disk space and WAL or replication lag. Retain ledger records until all supported readers can retire them.
3. **Make cache reuse authorization-preserving.** The process-local S3 cache currently scopes entries by endpoint and bucket. Define the key with an authorized principal or stable policy scope, canonical object and immutable version, and normalized byte range. Recheck access across execution contexts and credential changes. Replace linear eviction scans and charge key/entry overhead and allocation sizes. Bound copies at fill and lookup. Test simultaneous misses, duplicate fill accounting, small ranges and revocation. Consider shared caching after profiling proves a concurrency need and cross-process authorization can be enforced. [Cache](../../src/backend/access/lakehouse/core/pgdatalake-core/src/cache.rs) · [Storage scope](../../src/backend/access/lakehouse/core/pgdatalake-core/src/storage.rs)
4. **Keep metadata shortcuts narrow and move eligible computation to batches.** After COUNT is safe, profile q1 and q3 inputs. Start with batch COUNT and checked integer SUM on eligible single-table inputs. Use PostgreSQL aggregate identities, null and empty-input rules, transition types, overflow semantics and finalization. Apply only proven equivalent row filters before aggregation. Keep joins, volatile expressions, DISTINCT, and unsupported grouping and collation behavior in PostgreSQL. Design bounded group-state before expanding. Treat MIN/MAX footer statistics as pruning bounds until exact extrema and row visibility are proven. Truncated bounds and deleted extrema need verification. Add page-index and Bloom pruning after request accounting and differential tests. Keep the typed ABI versioned so a future execution engine can be evaluated against the same inputs.
5. **Profile each phase and preserve controls.** Expose sanitized per-plan counters for catalog/manifest calls, HEAD and ranged GET, fetched/consumed bytes, cache hits, delete work, decoded groups/batches, FFI rows/batches and upper-path output. Bound telemetry overhead. Capture symbolized CPU profiles and allocation or RSS samples for the query backend and workers. Retain build IDs for Rust and PostgreSQL frames. Measure planning and execution separately. Use those measurements to choose among projection, aggregation, join planning and cache work. Provide scoped switches to compare and roll back pushdown, elision and prefetch.

## Performance and release qualification

Extend the checked-in runner. Today it discards results, compares one fact-table count to a constant, warns and continues on mismatch, and labels skipped warmup as cold. The TPC-DS namespace option is unused in the workload. Attach explicitly pinned fixtures and fail before timing on a dataset, schema, snapshot or digest mismatch. Record the generator revision, layout and seed. Capture SQL hash, settings, build ID, backend/worker memory, cancellation status, object metrics and reference results. Canonicalize unordered results as multisets. Measure first execution and warm results separately, recording cache state. Retain failed runs and continue independent cases. Regenerate only in an explicitly selected disposable catalog. [Performance runner](../../scripts/perf/lakehouse_perf.py) · [Testing spec](10-testing.md)

| Case | Initial pass condition |
|---|---|
| Read correctness | Identical results with optimizations enabled and disabled across cold/warm caches, serial/parallel execution, time travel and delete formats. Independent readers verify exact row IDs in the cases used to claim support. |
| Metadata and LIMIT | Default EXPLAIN opens zero data/delete objects. Eligible COUNT opens zero data objects and matches the ordinary aggregate. Cold LIMIT 1 sends zero reads for later row groups. |
| Wide projection and scale | A one-column scan transfers fewer data bytes than the wide scan. At fixed width and batch size, live decoded bytes remain within budget as row group count grows 10×. Report process RSS and total memory at 1, 4 and 16 concurrent sessions. |
| Operations | Cancel blocked I/O and qualify publisher restart cases. On sustained inserts, report p95 foreground commit time, p95 and oldest pending age, publish throughput and memory/WAL growth. Show backlog drains after recovery. |
| Analytics | Complete SF10 q1–q10 and selective, wide, delete-heavy, partial-aggregate and correlated-rescan cases on the same pinned fixtures. Use at least five comparable warm runs and separate cold runs. Require exact results and completed canaries. Set latency and throughput targets on declared hardware after establishing a valid baseline. |

**Landing order.** First qualify COUNT and staged visibility or keep their affected paths gated. Then qualify lazy reads, cleanup, and request/memory telemetry. Use profile evidence to reduce repeated planning and add one exact batch-reduction path. Keep page indexes, broad aggregate support, compaction and shared caching as independent slices with their own tests. Complete M3 isolation and cloud parity as separate work, including real transport, credential rotation and the four-store fixture matrix. Follow the [TDD and smoke receipt requirements](10-testing.md#milestone-tdd-and-smoke-receipts) at every milestone.
