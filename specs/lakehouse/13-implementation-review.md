# Lakehouse FDW and managed Iceberg implementation review

**Decision, 2026-11-20. Hold production use.** A second managed append can overwrite a data file still referenced by the first snapshot. The new snapshot also omits earlier live manifests. The read-only FDW has independent release blockers in predicate pruning, delete application, parallel execution, and credential handling. An external table can return a plausible, incomplete result. Passing the current suites does not establish these properties.

**Baseline.** This review covers `lakehouse-dev` at `a9000592029`, including the change that removes credential names from managed table reloptions. It covers the SQL extension, FDW, managed TableAM, PostgreSQL time-travel and reloptions changes, C/Rust ABI, REST/OAuth, storage, Iceberg metadata and manifests, Parquet reader and writer, build, CI, and fixtures. FDW writes are absent. Findings about publishing snapshots concern the managed TableAM and the objects subsequently read by both paths. This document proposes changes for review. Requirements below describe acceptance criteria for future changes.

## Release blockers

### 1. Preserve every published snapshot and its objects

`BatchWriter::write_file` names a data file by row count and a session-local counter. `StorageIo::put_bytes` uses an ordinary PUT. Equal-size batches in separate transactions can overwrite one another even before the second catalog commit succeeds. Separately, `write_snapshot` constructs the entire manifest list from one newly produced entry. A parent snapshot ID records lineage but supplies no inherited files to a reader of the child. These are independent bugs. Fixing either alone leaves data loss possible. [Writer](../../src/backend/access/lakehouse/core/pgdatalake-core/src/writer.rs) · [Snapshot assembly](../../src/backend/access/lakehouse/core/pgdatalake-core/src/snapshot_write.rs)

Use a unique operation/file identity, enforce create-only semantics where supported, and keep the identity stable across retries of the same upload. Build an append against the exact base snapshot, carrying forward its live data **and delete** manifests. Compute file size and row count from the completed writer. `pg_datalake_write_flush` currently downloads the just-written file to measure it, treats a failed GET as zero bytes, and recovers the count from its name.

**Acceptance.** Append A, then B, first with equal batch sizes and then with different sizes. Current reads must yield A+B, and a pinned read of the first snapshot must still yield A. Aborting B after upload must leave both the bytes and visibility of A intact. Repeat with two writers and with an externally written base containing deletes. Check manifest paths, counts, and file hashes, then read both snapshots with an independent Iceberg reader.

### 2. Rebuild the commit against the verified base

`CatalogClient::commit_append` writes the manifest list, parent and sequence number before `commit_with_retry`. The retry closure reloads metadata and changes the requirements while cloning the original updates. It can even adopt a replacement table's UUID. When the response lacks inline metadata it derives an absent main snapshot. Snapshot IDs use the sequence and a millisecond remainder, allowing collisions. A successful POST followed by a lost or unreadable response has a different recovery procedure from a rejected precondition. [Session](../../src/backend/access/lakehouse/core/pgdatalake-core/src/session.rs) · [Commit protocol](../../src/backend/access/lakehouse/core/pgdatalake-core/src/catalog/commit.rs) · [Write FFI](../../src/backend/access/lakehouse/core/pgdatalake-core/src/ffi.rs)

Bind the operation to the original UUID. Use verified current metadata for each attempt, including the referenced metadata file when needed. Revalidate schema IDs, required fields, partition spec, format version and encryption support before accepting staged files. Initially allow only write formats and unpartitioned schemas the writer can actually emit. Regenerate base-dependent metadata and requirements together. Use a collision-resistant positive snapshot ID and record an operation ID for reconciliation. On an unknown commit outcome, verify remote state before retry or orphan cleanup.

**Acceptance.** Use a stateful mock that enforces requirements, then a real fixture catalog. Cover a competing append, table replacement, schema/spec change, missing inline metadata, a rejected commit, and an accepted commit whose response is lost. Check the resulting independent reader's row set, ancestry, sequence numbers, and the absence of duplicate append effects. The current mock that merges a first snapshot into empty metadata cannot establish these properties.

### 3. Make the managed transaction boundary explicit

`lakehouse_xact_callback` publishes each relation separately during PRE_COMMIT. A failure on the second relation, a later PostgreSQL abort, or a crash can leave a remote commit visible. No durable decision record or subtransaction callback accompanies the staged writes. An insert rolled back to a savepoint can remain staged. PREPARE tears down the state without a durable participant for COMMIT PREPARED. `create_remote` performs external DDL immediately. These semantics conflict with several guarantees in [the transaction spec](07-transactions.md). [TableAM transaction and staging code](../../src/backend/access/lakehouse/tableam.c)

Define the first supported contract narrowly. Reject prepared transactions with pending remote writes before prepare, support subtransaction rollback or reject writes in subtransactions before staging, and reject unsupported multi-table operations before publishing any remote table. Specify the mixed local/remote commit window, unknown outcomes, and operator reconciliation. A PostgreSQL error after external publication cannot undo the external commit. Require a reviewed recovery protocol before advertising atomic mixed transactions. Treat externally created namespace/table objects as explicit external effects and define retry and cleanup ownership.

**Acceptance.** Exercise SAVEPOINT/ROLLBACK TO, a caught statement error, PREPARE/ROLLBACK PREPARED, two remote tables where the second fails, and loss of the backend around publication. Observe from a separate PostgreSQL session and an independent catalog client. Record both outcomes and demonstrate the documented recovery path.

### 4. Remove unsafe predicate serialization and wrong-result pruning

`TranslateQual` allocates `strlen(raw) + 3` bytes and then inserts escape characters into that fixed buffer. It interpolates field names directly into JSON. The tag serializer misses control characters. Use PostgreSQL's JSON escaping with a growable buffer for all strings, or pass a typed representation. Avoid calling arbitrary type output functions while deciding pushdown eligibility. [FDW planner](../../src/backend/access/lakehouse/fdw.c) · [Rust pruning](../../src/backend/access/lakehouse/core/pgdatalake-core/src/scan.rs)

Operator spelling alone does not establish operator semantics. The code accepts same-named user operators, compares text using byte order regardless of SQL collation, sends PostgreSQL time values relative to 2000 to Iceberg comparisons relative to 1970, and serializes floats using `%g`. Rust converts long bounds and integer constants to `f64`. Adjacent bigints above 2⁵³ can then compare equal for a strict inequality. Identity partitions are matched by display name, without proving the transform's source field ID. An unknown partition spec falls back to the default spec, and a missing current schema with a predicate takes a `continue` that discards the file. Local SQL rechecks cannot recover a file the planner already eliminated.

Start with an allowlist of built-in operator identities, compatible PG and Iceberg types, and proven collation/ordering semantics. Use exact integer domains, checked epoch conversion, conservative NaN/infinity rules, and stable field IDs. Retain the file on inconclusive statistics. Report invalid required metadata explicitly. Keep all residual quals in the PostgreSQL plan.

**Acceptance.** For each pushed predicate compare ordered rows or a multiset digest against the same snapshot with pruning disabled. Include strict inequalities around 2⁵³, a non-UTC session, epoch boundaries, floats near a bound, collated strings, cross-type comparisons, a same-named operator with different semantics, unusual identifiers, evolved partitions, and missing bounds. Include unit coverage of the safe string encoder under an instrumented build.

### 5. Apply Iceberg deletes and schema evolution by field ID

`load_row_deletes` uses every column in an equality-delete Parquet file, although the manifest already supplies `equality_ids`. Additional non-key columns can prevent a valid delete from matching. Position deletes retain path/position without sequence or partition applicability. The empty-projection branch in `pg_datalake_rows_open` calls `open_all` and loses position deletes. `partition.is_some()` conflates an empty partition record with a partitioned spec. Scan planning applies data predicates before distinguishing data and delete entries. Prove a delete-specific pruning rule before eliminating any delete task. [Scan planner](../../src/backend/access/lakehouse/core/pgdatalake-core/src/scan.rs) · [Reader](../../src/backend/access/lakehouse/core/pgdatalake-core/src/parquet.rs) · [Iceberg scan planning and delete semantics](https://iceberg.apache.org/spec/#scan-planning)

Bind projected and delete fields to Iceberg IDs and the file's schema, including renamed columns, name reuse, permitted type promotion, and missing optional fields/defaults. Use the selected snapshot and projection semantics explicitly. Decode manifest inheritance, including valid null snapshot IDs where the enclosing manifest supplies the ID. Retain delete spec, partition, data sequence number, and referenced file identity. Use separate paths for unpartitioned/global equality deletes, scoped equality deletes, and position deletes. Identify unsupported file formats, v3 deletion vectors and required features before returning rows.

Correct the wire model before extending it. Serde derives `default-partition-spec-id` where Iceberg supplies `default-spec-id`; the tests repeat the misspelling and the writer falls back to spec zero. The map codec expects `keys` and `values` instead of the wire members `key` and `value`. List and map models discard nested field IDs and requiredness. A valid map can therefore prevent loading an otherwise readable table even when a query selects only a primitive column. Add independently generated metadata with a nonzero default spec and nested fields. [Metadata codec](../../src/backend/access/lakehouse/core/pgdatalake-core/src/catalog/metadata.rs) · [Iceberg JSON serialization](https://iceberg.apache.org/spec/#appendix-c-json-serialization)

**Acceptance.** Compare with an external reader using a delete file with an extra non-key column, renamed or absent projected fields, same-sequence position deletes, older/equal/newer equality deletes, global and partition-scoped deletes, and zero projected columns. Test mixed historical specs, null keys and a snapshot containing unsupported delete storage. Check exact survivor IDs.

### 6. Bind credentials, destinations and SQL privileges to the same principal

The SQL-installed object exposes an FDW handler. The example creates its wrapper without a validator. `ExtractOptions` reads literal bearer/S3 credentials from server/table options and permits a table-level storage endpoint override. It never resolves a user mapping. The managed parser at this revision removes literal credential names from `pg_class.reloptions`, but `managed_tables` and `attach_table` still carry secrets, and identity merging can combine credentials with a separately supplied destination. Catalog configuration also contributes endpoint/key fields. This violates the design's secret-reference and authority model. [SQL surface](../../src/backend/access/lakehouse/lakehouse--1.0.sql) · [FDW options](../../src/backend/access/lakehouse/fdw.c) · [Config merge](../../src/backend/access/lakehouse/core/pgdatalake-core/src/session.rs) · [Existing security design](09-security.md)

Ship a canonical wrapper and per-catalog option validator. Define who may set each option, reject unknown/misplaced options at DDL, and validate legacy definitions again on use. Bind storage scope, approved egress and credential reference to the server/mapping and effective permission-checking user, including view-owner versus invoker semantics. A grant of SQL SELECT grants access to its relation within that scope. Require explicit trust for ambient cloud credentials. Use controlled references for secrets and migrate existing literal credentials with an operator-visible rotation procedure. Never copy secret values to plans, DSM, diagnostics or dump examples.

`open_for` accepts catalog- or manifest-supplied local paths; the S3 builder enables HTTP. REST uses default redirect behavior, and multiple errors surface raw URLs or response bodies. Apply a shared scheme, origin, bucket and path policy to each hop, including catalog redirects and delegated metadata/data/delete locations. Keep a local object store for explicitly opted-in fixtures. Redact URL userinfo/query values and remote bodies. Resolve optional OAuth configuration explicitly. The FFI uses static tokens, and refresh failures can yield an empty or expired token in the optional provider. [Storage policy](../../src/backend/access/lakehouse/core/pgdatalake-core/src/storage.rs) · [REST client](../../src/backend/access/lakehouse/core/pgdatalake-core/src/catalog/rest.rs) · [OAuth provider](../../src/backend/access/lakehouse/core/pgdatalake-core/src/catalog/oauth.rs)

`scan_files` takes a caller-chosen endpoint and credentials. `create_remote(regclass)` checks AM and relkind but lacks an explicit ownership check before reading the attachment and issuing external DDL. The SQL installs no explicit function EXECUTE revocations. Effective exposure depends on schema USAGE and grants. Provide a relation/server-based inspection API with normal ACL checks, restrict low-level functions, require owner or delegated management authority for remote creation, and type conflict responses instead of searching error strings for “409”. Test the invoker-rights DROP event trigger with ordinary owners; its unconditional DELETE on the private mapping table can interfere with unrelated DDL. Granting public write access to mappings would expose a larger problem.

**Acceptance.** Use separate owner, reader, mapping administrator, and unrelated roles plus inert mock transports. Verify denied operations perform zero I/O, legitimate views select the intended mapping, configuration overrides cannot repurpose a credential, and a reader cannot initiate remote DDL. Verify unrelated DROP works. Inspect ACLs, EXPLAIN, captured diagnostics and dump output using sentinel strings. Confirm the documented five-argument listing works and distinguishes an empty snapshot from invalid configuration.

### 7. Give each scan its own work queue and immutable snapshot

`lakehouse_shared_state` is a process-global pointer used by Iterate whenever non-NULL, including nodes that did not initialize it. Two nodes can claim from one another or clear one another's state. Workers separately call `lakehouse_OpenSession` and plan the latest snapshot, then share only a numeric index. Concurrent commits can make index N refer to different files. `GetForeignPaths` unconditionally adds a two-worker partial path even though PostgreSQL asserts `consider_parallel` for partial paths. [FDW DSM and planner](../../src/backend/access/lakehouse/fdw.c) · [PostgreSQL path invariant](../../src/backend/optimizer/util/pathnode.c) · [FDW callback contract](https://www.postgresql.org/docs/current/fdw-callbacks.html)

Disable the partial path until the leader owns a per-node immutable task set and workers receive a stable task mapping. Resolve a named ref or “current” to a concrete snapshot at execution. Coordinate scans of the same remote table within a statement and specify stronger isolation behavior. Cached plans require a fresh execution pin at the appropriate boundary. Keep coordination on the correct executor node across initialize/reinitialize/rescan/shutdown, including early termination. Use only eligible, parallel-safe paths and mappings.

**Acceptance.** Compare full result multisets to serial execution for self-joins, two distinct foreign scans, a serial node alongside a parallel node, correlated rescans, and leader participation on/off. Advance the catalog after leader initialization using a test barrier. Every expected row must appear exactly once per logical scan. Run under assertions with parallel execution disabled too.

### 8. Preserve type values and errors across C, Rust and PostgreSQL

`pg_datalake_rows_next` converts a caught panic into false, the same result as EOF. Unsupported Arrow types become SQL NULL. LargeUtf8/LargeBinary share downcasts for their small-offset counterparts, and 16-byte fixed binary is always rendered as UUID. An interior NUL can become an empty CString. C passes typmod `-1` to input conversion. On writes, `name` is routed through `textout` despite its different Datum representation. Dropped attributes are omitted from the schema but included in the row. The decimal builder gets an unscaled integer from the textual fractional digits without reconciling the target scale. Write-side exported functions also lack the consistent panic boundary used by scan-open. [ABI](../../src/backend/access/lakehouse/core/pgdatalake-core/src/ffi.rs) · [Type reader](../../src/backend/access/lakehouse/core/pgdatalake-core/src/parquet.rs) · [Writer](../../src/backend/access/lakehouse/core/pgdatalake-core/src/writer.rs) · [PostgreSQL conversions](../../src/backend/access/lakehouse/tableam.c)

Define explicit ROW/EOF/ERROR status with owned, bounded diagnostics. Use field type, ID, typmod, nullability and encoding to drive conversion. Make unsupported combinations fail before rows are returned. Define non-UTF8 database handling and PostgreSQL-inexpressible data. Use a counted array of fields instead of comma-separated names. Validate an entire write row before mutating any column builder. A failed later cell currently leaves earlier builders advanced. Use the proper PostgreSQL type routines or typed values, including bytea independent of `bytea_output`.

**Acceptance.** Test the C/Rust boundary with round trips checked by an independent reader for supported types, NULL versus empty, fixed[16] versus UUID, scale-changing numeric, quoted/comma-containing names, fast-path timestamp/date extremes, and dropped attributes. Unsupported types and reader failures after earlier rows must abort the statement with a useful SQLSTATE. Verify a failed row cannot corrupt the next valid batch.

## Performance work with measurable outcomes

1. **Reduce planning I/O before tuning costs.** `GetForeignRelSize` builds a complete unfiltered session, reads manifests and eagerly materializes delete files, sums counts and frees it. Begin repeats the work, including for plain EXPLAIN, and workers repeat it again. Use a cheap estimate from catalog summaries or bounded statistics, with an optional, documented remote-estimate policy. Resolve the executable task list once per scan at the correct snapshot boundary. Distinguish base tuples from filtered cardinality. Price startup latency, surviving bytes, CPU conversion and worker startup. Gate partial paths on enough independent work. Report estimates separately from actual files, bytes, rows and time. Update the hard-coded “projection only” EXPLAIN output. **Measure** GET counts for EXPLAIN, LIMIT and a join, and actual versus estimated rows for selective/unselective queries. A plain EXPLAIN should require zero data/delete-file GETs under the default policy. [FDW planning and EXPLAIN](../../src/backend/access/lakehouse/fdw.c)

2. **Bound scan memory and implement physical projection.** Begin requests every live SQL attribute. Rust fetches the whole compressed object into memory, copies the bytes, builds a Parquet reader without a projection mask, then collects every decoded batch. Selecting a single column or the first row still incurs whole-file work. Equality deletes are cloned per task, then scanned per candidate row. Use ranged reads, footer-driven column selection (output, residual quals and delete keys), an incremental batch iterator and a bounded per-scan budget. Reuse object-store clients within credential scope. Group equality keys by field-ID set and applicability, use a typed hash membership test where valid, and spill or return a bounded-resource error on large inputs. Apply decompression limits to metadata, manifests, and remote response bodies as well. **Measure** first-row latency, bytes fetched, range count, peak RSS and delete CPU as file width, row groups and delete cardinality grow. With fixed batch size, peak live decoded data must plateau as more row groups are added. [Storage reads](../../src/backend/access/lakehouse/core/pgdatalake-core/src/storage.rs) · [Parquet reader](../../src/backend/access/lakehouse/core/pgdatalake-core/src/parquet.rs)

3. **Remove per-cell conversions on the hot path.** Rust allocates a CString per cell, the FDW calls a PostgreSQL input function per value, then forms a heap tuple with temporary arrays. Start with typed primitives and a batch ABI with explicit ownership and null bitmaps, preserving typmods and exact SQL values. Fill a slot of the kind promised to the executor and document the lifetime of by-reference values. Keep a checked fallback for uncommon types. Apply byte/row flush thresholds to the managed writer and a spillable own-write overlay. Today it buffers both Rust column builders and copied PG Datums, grows PG arrays in increments of 64 and flushes at commit on the SQL path. Use the primary-key index for attachment lookup instead of scanning the heap per open. **Measure** CPU per million rows, peak backend RSS during COPY/INSERT, bytes uploaded, and rescan work. Avoid interpreting faster runtimes with missing rows as an improvement. [FDW iterator](../../src/backend/access/lakehouse/fdw.c) · [Renderer](../../src/backend/access/lakehouse/core/pgdatalake-core/src/ffi.rs) · [TableAM staging](../../src/backend/access/lakehouse/tableam.c)

4. **Establish a reproducible comparison.** The recorded SF10 q3 run was terminated after over 60 minutes. The ten completed queries used smaller samples, and q6 also reduced a dimension. These are distinct workloads. Store dataset seed, scale, snapshots, row counts, query text, client/server settings, worker count, layout, reference result digests and object-cache conditions. Compare a multi-file narrow scan, wide scan, selective filter, equality-delete scan, rescan join and repeated append. Collect five runs per case and publish median/range plus peak RSS and bytes. Agree on target hardware and budgets before introducing latency pass/fail thresholds. [Recorded TPC-DS evidence](../../src/test/lakehouse/fixtures/gate-evidence-m1-tpcds.md)

**Changes to the existing design documents for the implementing agent**
