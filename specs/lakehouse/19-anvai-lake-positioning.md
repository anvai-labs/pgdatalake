# Anvai Lake competitive positioning and product gates

**Recommendation.** Sell access and reliable publication between the PostgreSQL customers already operate and the Iceberg catalogs they already use. Match the ease of setup and operational feedback offered by managed products. Earn an advantage by letting the customer verify a specific Iceberg snapshot independently, across engines, with clear freshness and recovery behavior. This is a strategy to test, and the current fork has release blockers.

The acquisitions validate competition for the workflow. They do not establish demand for a fork, broad cross-catalog DML, or willingness to switch. The relevant names are **Neon** for serverless PostgreSQL, **Mooncake Labs** for the acquired analytics team, and **`pg_mooncake` and Moonlink** for its open-source components. Databricks announced both transactions. [Databricks and Neon](https://www.databricks.com/blog/databricks-neon) · [Databricks' Mooncake Labs announcement](https://www.linkedin.com/posts/databricks_were-excited-to-announce-that-databricks-activity-7379138538652696576-2pbr) · [pg_mooncake](https://github.com/Mooncake-Labs/pg_mooncake) · [Moonlink](https://github.com/Mooncake-Labs/moonlink)

| Alternative | Strength and current scope | Implication for Anvai Lake |

Database branch provisioning is outside the initial scope. [Neon platform](https://neon.com/blog/neon-backend-is-ga) |
| **Databricks Lakebase and LTAP** | Hosted Postgres integrated with Unity Catalog. Synced tables serve lakehouse data in read-only PostgreSQL copies. Availability varies by cloud. | Treat this as the closest platform competitor for the integrated workflow. For an all-Databricks customer, its bundled governance, deployment and query path may be the better fit. Offer integration for customers bringing their own Postgres, storage or catalog. Benchmark actual eligible features and distinguish direct reads from materialized copies or change history. [LTAP capabilities and availability](https://docs.databricks.com/aws/en/oltp/projects/ltap-overview) · [Synced tables](https://docs.databricks.com/aws/en/oltp/projects/sync-tables) |
| **Mooncake Labs / pg_mooncake + Moonlink** | PostgreSQL-to-columnstore mirroring with DuckDB-powered analytics, and a CDC ingestion path that publishes Iceberg v3 with DVs. [pg_mooncake](https://github.com/Mooncake-Labs/pg_mooncake) · [Moonlink](https://github.com/Mooncake-Labs/moonlink) |
| **Snowflake pg_lake** | The closest open-source extension comparison. This is a workflow comparison. It makes no claims about unpublished vendor roadmaps, relative performance, or catalog coverage a pilot has yet to demonstrate. Verify edition, region, preview access and versions for each measurement.

## 2. Recommended product sequence

1. **Read into the existing environment.** Start with a stock PostgreSQL FDW package and a customer-operated catalog. Provide connection validation, least-privilege setup, schema import or a generated table definition, and pinned-snapshot verification. Time this against pg_lake and the customer's existing alternative. The full fork must justify each required patch in the managed lane.
2. **Add an ingestion path for existing heap tables.** Keep the application's INSERT, UPDATE and DELETE on PostgreSQL heap tables with local MVCC, indexes and constraints. Evaluate a logical-decoding/CDC connector with initial backfill, progress checkpointing, replay, replica identity and schema-evolution handling. Start with append-only events or a change log. Offer a distinct **current-state mirror** only after exactly applying deletes and updates. Consider reusable components and licensing, then decide based on correctness, operational ownership, and catalog support.
3. **Qualify the managed TableAM where direct access matters.** Target append-heavy tables and isolated corrections that benefit from owning the Iceberg table directly. Give users a managed current view and an explicit published view. Fix visibility and recovery before enabling broader DML. A feature-rich TableAM that needs a server replacement has higher adoption cost than capturing supported writes from an existing service. Compare both with customer pilots before committing to an architecture for all users.
4. **Make one catalog profile excellent, then prove portability.** Use the same read and publish checks on Lakekeeper and AWS Glue/EMR. Qualify Unity Catalog and Snowflake separately where demand warrants. Version and test credentials, file formats, supported writes, delete reads and refresh behavior for each. A second independently validated deployment profile provides evidence for portability.

Use an install-and-query preview for engineering adoption. Evaluate paid support, managed operations, and visibility/recovery tooling where pilots show buyer demand. Customers that cannot install native code need a separately qualified CDC delivery path or provider support. The [adoption spec](17-anvai-lake-product.md#5-addressable-market-and-adoption-friction) describes how to count eligible accounts.

## 3. Parity to establish and advantages to earn

| Customer expectation | Parity gate | Advantage hypothesis and proof |
|---|---|---|
| First query and safe evaluation | Clean install or connector setup, one documented least-privilege mapping, candidate upgrade and rollback test. | Keep a live PostgreSQL deployment and catalog. Show the exact same snapshot from two engines during the pilot without rewriting or rehosting the source. |
| Fresh analytics on changes | Distinguish INSERT, UPDATE and DELETE capture, first local visibility, publish, and consumer refresh. Support backfill and resume for the CDC lane. | Give every publication unit a receipt with a verified snapshot ID, stable wait/retry semantics and an observable reason when it is late. Prove no duplicate or missing effect after a catalog response is lost. |
| Practical operational behavior | Exercise a representative outage, slow consumer, growing WAL/queue, credential rotation and upgrade. | Show predictable storage and operational cost under backlog. Preserve explicit policy and deployment ownership across two certified catalog profiles. |
| Useful mutation UX | Match application DML in the heap lane. Publish a precise per-operation support matrix for managed tables. | On a proven append or correction workload, demonstrate equivalent rows with lower latency, I/O or operator effort. Publish how COW, MoR and staged updates differ, and keep the escape path to ordinary heap DML. |
| Analytical performance | Use matched snapshots and result digests. Profile wide, selective, aggregate, and delete-heavy reads. | Demonstrate an improvement only under equal semantics, hardware/cost envelope and load. An internal metadata count or warm microbenchmark cannot stand in for a customer-facing mixed workload. |

**Positioning to test with design partners.**

> Keep your PostgreSQL deployment and Iceberg catalog. Query a specific Iceberg version from PostgreSQL and publish app data with a snapshot receipt your downstream engine can verify.

The likely buyer is a platform or data engineering lead at an organization with an existing PostgreSQL estate and at least one independently operated Iceberg consumer. The best first projects are read access to landed Spark tables and append-heavy operational ELT. Test the pitch against the buyer's actual alternative. A customer who mainly wants instant database provisioning or uses Unity Catalog across the entire stack has a different set of priorities.

## 4. Pilot and benchmark gates

For a small set of design partners, choose one scoped workload per partner and have a second operator repeat the setup using only the runbook. Measure connection setup, elapsed time to a correct result, time to first catalog snapshot, credential steps, rollback effort, and how many operators can diagnose a delayed row without engineering help. Retain positive and rejected pilots with the reason. Before promoting a paid offer, require a repeated successful workflow on representative data and a buyer willing to run it beyond the trial.

| Comparison | Workload and receipt |
|---|---|
| **Stock attachment** | Query the same external Iceberg snapshot through Anvai Lake, pg_lake where supported, and an independent engine. Include install time, granted privileges, rows, planning/first-row latency, GETs, bytes and peak memory. |
| **CDC/current-state mirror** | On the same heap insert/update/delete workload, compare Anvai Lake's qualified lane with Moonlink where available and the customer's CDC path. Measure foreground p50/p95, publication and consumer lag, replica-identity limitations, change throughput, WAL/queue bytes, and total cost for the same correctness and lag target. |
| **Managed ecosystem** | If the pilot has Lakebase and feature access, compare its eligible current-state or change-feed path with Anvai Lake under a matching requirement. Keep reverse sync distinct from direct Iceberg query. Record region and preview availability. |
| **Recovery and erase semantics** | Kill after catalog commit, restart, and verify current and historical row states in the originating PostgreSQL and an independent consumer. Measure recovery time, backlog drain and any manual action. Separately verify snapshot expiry and retention claims. |

Pin source and target versions, workload, data layout, file sizes, catalog, format version, permissions, caching and concurrency. Report correctness before performance and distinguish local visibility, verified publication and first external read. Run the test-first and measured smoke gates in the [testing spec](10-testing.md#milestone-tdd-and-smoke-receipts) and [DML contract](18-anvai-lake-dml.md#7-milestones-and-gates).

The first competitive release requires a stock or clearly packaged install, an independently verified Iceberg read, and a recoverable append handoff. The next release adds a proven heap CDC path or qualified direct corrections according to pilot demand. Defer broad managed UPDATE/DELETE until operation identity, snapshots, recovery and measured amplification support the promise.
