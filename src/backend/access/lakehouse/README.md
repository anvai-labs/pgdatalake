# lakehouse FDW + managed TableAM — internals, testing, troubleshooting

This is the engineer-facing entry point for the two things this directory adds
**beyond core PostgreSQL**:

1. a **read-only FDW** (`lakehouse_fdw`) that reads external Apache Iceberg
   tables through a REST catalog (runs on stock PG and the fork), and
2. a **managed TableAM** (`USING lakehouse`) on the fork: tables stored
   natively as Iceberg, written through a staged publisher, read through a
   snapshot-exact "managed cut".

Design rationale and acceptance specs live in `specs/lakehouse/modules/`
(start at `modules/README.md`; managed visibility is
`modules/03-managed-visibility.md`). This file covers how the code actually
behaves, how to run the tests, and how to debug when it misbehaves.

### Extension SQL (migrations = behavior)

`lakehouse--1.N--1.N+1.sql` files are authoritative for ledger schema and SQL
functions. Key objects (as of 1.19):

- `managed_capture_state` / `managed_capture_bindings` / `managed_read_anchors` — enrollment ledger (active binding + generation, lineage, anchor snapshot)
- `lakehouse_delta_segments` — staged, **sealed** segments awaiting publication (payload immutable)
- `publication_attempts` / claims — durable publication state machine
- `managed_read_grants` + `grant/revoke_managed_read` + `admit_managed_read(regclass, regrole)` — operator read grants and executor admission (SECURITY DEFINER; the `reader` argument is the CHECKED role, so a definer view cannot widen admission)
- STABLE helper functions that are snapshot-exact under pushed snapshots: `get_managed_read_scope`, `get_managed_read_visible_segments`, `get_managed_read_additions`, `get_managed_read_pending_head`, `load_managed_read_overlay`, `get_managed_read_segment_retention`

## The two read paths

### External (FDW) path

`plan` (`fdw_plan.c`) builds a ForeignScan with `fdw_private` carrying the
count-exec selector and table identity → `BeginForeignScan` (`fdw.c`) does
**no I/O** → first `IterateForeignScan` (`fdw_exec.c`) opens the session,
proves delete eligibility, resolves the pinned snapshot and only then reads
manifests/Parquet. This is why `EXPLAIN` and `LIMIT 0` are zero-request.

### Managed (TableAM) path — the life of a bound scan

1. **scan_begin** (`tableam.c:~1850`): bound gate runs *before* identity
   decode — bound tables must not resolve the querying user's mapping.
   Catalog-local declines (each 0A000, zero origin requests): parallel plans,
   scan keys, inheritance, RLS, own staged writes, non-staged write modes.
   Then **admission**: `lakehouse.admit_managed_read(rel, checked_role)` under
   the ledger owner's context, using the statement's active snapshot.
   Unadmitted → historical 0A000.
2. **Demand-time cut install** (`install_managed_cut`, first `getnextslot`):
   `EXPLAIN`/`LIMIT 0` never reach it; every failure precedes the first row.
   - **Step 0 — preflight (zero origin contact):** `get_managed_read_scope`
     (STABLE → honors pushed snapshots) probed under BOTH the statement's
     registered snapshot and a fresh one. A reader whose snapshot predates a
     binding rotation fails 55000 *before* the observation makes a request.
   - **Step 1 — observe (the only catalog contact):** one bounded GET with
     `purpose=read` credentials; certifies the pin ancestry.
   - **Step 2 — fresh-proof frame:** registered fresh snapshot
     (`RegisterSnapshot(GetLatestSnapshot())`), owner-switched. Direct grant
     recheck (see snapshot rules below), certified addition chain, pending-head
     proof. Head moved past the accepted child → fallback to retained parent
     with the full overlay, `proved=false`.
   - **Step 3 — statement frame:** the *registered statement snapshot*: visible
     segments + payload retention.
   - **Steps 4–6 — select, overlay, plan:** pure-FFI compatible-pin selection;
     sha256-verified overlay payloads into the staged-delta side; `plan_exact`
     consumes the observation into the scan session.
3. **Serving:** own staged rows → staged deltas (overlay, `delta_loaded=true`
   even when empty — prevents double-serve of unpublished segments) → base
   tasks. **rescan rewinds with zero re-admission and zero catalog
   resolutions**; `cut_installed` guards the install. Backward fetches on a
   scroll cursor come from the Sort tuplestore (so rescan drills need an
   open statement: cursor + nested loop whose *inner* side is the scan).
4. **release:** drops the read observation, closes delta handles.

### COW mutations (UPDATE/DELETE on published rows)

`lakehouse_tuple_update` / `lakehouse_tuple_delete` (tableam.c) capture a
**tombstone** of the observed file/ordinal — UPDATE also stages the
replacement row — and PRE-COMMIT (`lakehouse_xact_callback`) rebuilds each
touched file without the tombstoned rows and commits **one overwrite
snapshot** (`pg_datalake_write_commit_overwrite`) with assert-ref
requirements. Outcome codes: `0A000` unsupported profile (delete-bearing
source snapshot, mutating a row inserted in the same transaction, FOR
UPDATE, two-phase); `40001` the commit base moved — the concurrent external
writer wins, no partial state; `40003` ambiguous remote commit
(lookup-only recovery, never re-appends). Routing-by-inspection ("does the
row live in the base or in staged rows?") decides *which* subsystem handles
the row; the commit assertion decides whether it *may* — a pre-read alone
is TOCTOU-unsafe.

**Operator caveat:** every COW mutation rewrites the files it touches.
Mutation volume grows dead bytes and file counts until compaction/optimize
lands (M4). Reads stay exactly correct at every snapshot — this is an
administration concern (the heap-bloat→vacuum trade, in Iceberg form), not
a correctness limit. Batch point mutations; watch small-file debt.
Contracts: [spec 18 §3a–3c](../../../specs/lakehouse/18-anvai-lake-dml.md);
boundary fixture: `cow-boundary-check.py`.

Error codes: 0A000 unsupported shape / unadmitted · 42501 grant structure
rejected · 55000 admission/scope changed under the scan or no compatible cut ·
54000 budgets exceeded. **Segments are sealed** — the 55000-consistency shape
is rotated scope, never payload reclamation.

## Snapshot discipline (read this before touching SPI)

There are three distinct snapshots and they must not be confused:

| Snapshot | Who | Governs |
|---|---|---|
| Statement/registered snapshot | the reader's transaction (held under RR) | which local ledger rows and *data* the statement sees; visible-segment/overlay loads |
| Fresh snapshot | `RegisterSnapshot(GetLatestSnapshot())` inside install | whether the operator's grant/enrollment **still stands right now** (authorization is a point-in-time decision, deliberately not part of the reader's repeatable view) |
| Catalog pin | Iceberg `snapshot_id` in the REST catalog | which Iceberg data files the cut reads (parent pin, child pin, overlay members) |

**The VOLATILE-SQL-function trap (cost a real bug — #93 review F1):** a
`LANGUAGE sql VOLATILE` function's body is executed by
`executor/functions.c` with `PushActiveSnapshot(GetTransactionSnapshot())`.
In a REPEATABLE READ scan that is the *held* snapshot — **no matter which
snapshot the caller pushes** via `SPI_execute_snapshot`. A revoked grant
therefore stayed invisible to a recheck that called
`admit_managed_read`, while the *direct* query on `managed_read_grants`
(whose heap scans use the pushed snapshot) saw it. Rules:

- For snapshot-exact reads, **inline the SQL in the `SPI_execute_snapshot`
  call**. Only STABLE/IMMUTABLE functions honor the pushed snapshot.
- `admit_managed_read` cannot be made STABLE: it calls volatile
  `clock_timestamp()`.

**SPI frame rules (each of these cost a segfault once):**

- Never run a second `SPI_execute*` in the same frame before consuming the
  previous query's `SPI_tuptable`/`SPI_processed` — the second call clobbers
  both. Read results *before* the next query.
- Guard `SPI_getvalue`/`SPI_getbinval` on `SPI_processed` — indexing
  `vals[0]` of an empty result is `heap_getattr(tup=0x0)`.
- Anything consumed after `SPI_finish` must be allocated with
  `MemoryContextAlloc(scan_context, …)` *inside* the frame (or copied there
  after): `SPI_connect` switches to the procedure context and `SPI_finish`
  **deletes it**. `palloc` after an `SPI_execute` call lands in the frame
  context and dies with it; `repalloc` keeps the chunk's original context.
- Snapshot stack balance: every `PushActiveSnapshot` needs exactly one
  `PopActiveSnapshot`; `RegisterSnapshot` before `PG_TRY`, unregister in
  the epilogue. An orphaned pop crashes later, at `PortalRunSelect`, far
  from the cause.

## Testing

### Regression suite (fast gate)

```
ninja -C build3 src/backend/access/lakehouse/lakehouse.so
meson test -C build3 --suite postgresql:lakehouse   # 11 subtests
```

### Fixture drills (`src/test/lakehouse/fixtures/`)

Each `*-check.py` proves one behavior end-to-end through ordinary SQL against
a fixture cluster (Lakekeeper-compatible REST gateway, MinIO, Trino). Common
environment:

```
export PGHOST=/tmp/anvai-managed-cut-host PGPORT=5599
export PATH=/path/to/build3/tmp_install/usr/local/pgsql/bin:$PATH
export LD_LIBRARY_PATH=/path/to/build3/src/interfaces/libpq   # psql needs built libpq
python3 <check>.py --worker <repo>/src/backend/access/lakehouse/core/target/release/examples/bound_publication_fixture
```

The fixture server runs from `build3/tmp_install` — **it loads whatever
`lakehouse.so` is installed there**, not your working tree.

Key drills: `managed-cut-sql-check.py` (the managed-cut drill: held-snapshot
trio with exact pin/overlay evidence, rescan-retained-cut, mid-window
revocation, nested SPI, rotated-scope 55000), `managed-capture-binding-check.py`
(enrollment/rotation/WAL recovery; run with `--provider --restart-fixture "$PGHOST/data"`),
`fdw-count-check.py` (stock-PG19 read-only package; needs a separate stock
cluster), `publication-*-check.py` (send admission/claims/discovery/ledger),
`catalog-reply-loss-check.py` (the lost-reply barrier).

Gotchas baked into the drills: held RR sessions need an immediate
`SELECT 1` to pin their snapshot; held sessions' AccessShare locks block
rotation's ACCESS EXCLUSIVE (commit them first); a login runner returns
*lists of lines*; keep `client_min_messages` at default in asserted sessions
or DEBUG lines break error-marker assertions.

## Troubleshooting playbook

**"My fix isn't running" — stale `.so`.** The single most common trap. The
server loads `build3/tmp_install/.../lakehouse.so`. After editing C code:
build → `meson test -C build3 --suite postgresql:setup` (installs) → restart
the fixture server → verify:

```
ls -la build3/src/backend/access/lakehouse/lakehouse.so \
      build3/tmp_install/usr/local/pgsql/lib/x86_64-linux-gnu/lakehouse.so
# prove what a backend actually loaded:
psql -c "SELECT pg_backend_pid()" -c "LOAD 'lakehouse'" -c "SELECT pg_sleep(15)" &
grep lakehouse /proc/<pid>/maps
```

**"Revoked/expired reader still sees rows."** Check the visibility layer
first: `SELECT xmin::text::bigint, revoked FROM lakehouse.managed_read_grants …`,
compare against `txid_current()` of the revoking transaction, and remember
the VOLATILE trap above. Server-side forensics: restart the fixture server
with `-c log_min_messages=debug1` and read `server.log` (client-side
`client_min_messages = debug1` pollutes runner assertions — prefer
server-side).

**Per-scan evidence.** `SELECT lakehouse.managed_read_cut_evidence()` returns
the backend-local `{"pin", "proved", "overlay"}` of the last installed cut —
read it in the same batch as the scan it should explain.

**Savepoint anomalies (3B001 "savepoint does not exist") during drills** are
almost always a *downstream symptom* of an earlier unexpected error in the
same session (the abort path consumed the subtransaction stack). Fix the
first unexpected error; the savepoint error follows.

**Catalog I/O counts.** The drills assert exact GET/POST counts through the
gateway. A scan's observation is the only reader-side GET; the writer's
publication is the only POST. Extra requests = a double-open or an
unintended resolution.
